Модель взаимодействия

Клиент-серверная модель

  • Сервер работает постоянно и ожидает подключений на заранее известном порту
  • Клиент подключается по необходимости и всегда инициирует обмен
  • Один сервер обслуживает множество клиентов одновременно

История: от ARPANET до POSIX

  • 1969 — ARPANET: первая сеть с коммутацией пакетов
  • 1974 — Сёрф и Кан: идея протокола TCP
  • 1981 — RFC 791 (IP) и RFC 793 (TCP) — действуют по сей день
  • янв. 1983 — «флаг-день»: ARPANET полностью переходит на TCP/IP
  • авг. 1983 — BSD 4.2: интерфейс сокетов вместе со стеком TCP/IP
  • 1990-е — POSIX закрепляет API; WinSock переносит его в Windows

Типы сокетов

Два типа сокетов — два протокола

SOCK_STREAM → TCP

  • непрерывный двунаправленный поток байтов
  • доставка подтверждается, потери восстанавливаются
  • порядок байтов гарантируется

SOCK_DGRAM → UDP

  • отдельные самостоятельные дейтаграммы
  • доставка и порядок не гарантируются
  • минимальные накладные расходы

Тип задаётся при создании сокета и определяет транспортный протокол

Сокетный API

Сервер: жизненный цикл

socket→ bind→ listen→ accept→ recv / send→ close
  • bind — зарегистрировать адрес и порт за сокетом
  • listen — перейти в режим ожидания; ядро ведёт очередь входящих подключений
  • accept — принять подключение из очереди; возвращает новый сокет — слушающий продолжает работу

Сокетный API

Клиент: жизненный цикл

socket→ connect→ send / recv→ close
  • connect — установить соединение: ОС выбирает свободный эфемерный порт и выполняет рукопожатие
  • после connect сокет готов к обмену в обоих направлениях
Connection refused — на порту нет слушателя Timeout — узел недоступен или не отвечает

↓ Доп. факт

Полный echo-сервер на Java

try (ServerSocket server = new ServerSocket(8080)) { // bind + listen
    while (true) {
        Socket client = server.accept();            // ждём подключения

        new Thread(() -> {                          // каждому клиенту — поток
            try (Socket c = client) {
                var in  = c.getInputStream();       // recv
                var out = c.getOutputStream();      // send
                int b;
                while ((b = in.read()) != -1) {
                    out.write(b);                   // эхо-ответ
                }
            } catch (IOException e) { /* клиент отключился */ }
        }).start();
    }
}

↓ Доп. факт

SYN flood и SYN cookies

  • SYN flood: атакующий шлёт SYN и не отвечает на SYN+ACK; сервер копит полуоткрытые соединения и расходует ресурсы
  • SYN cookies: сервер не хранит состояние, кодируя его в номере seq ответа — подлинный клиент восстановит соединение, атакующий — нет

Транспорт · TCP

Флаги TCP-сегмента

SYN
установка соединения, синхронизация начальных номеров
ACK
поле подтверждения значимо — почти все сегменты после установления
FIN
корректное закрытие одного направления передачи
RST
немедленный аварийный сброс соединения
PSH
передать данные приложению без ожидания накопления

RST приходит при подключении к незанятому порту, при аварийном завершении собеседника, при записи в закрытое соединение

Транспорт · TCP

Буферы и надёжность доставки

приложение→ send()→ буфер отправки→ сеть→ буфер приёма→ recv()→ приложение
  • send лишь копирует данные в буфер ядра — дальнейшую передачу ведёт TCP
  • буферы есть у каждой стороны: отправка и приём асинхронны друг другу

1. Подтверждения

каждый байт учитывается; ACK = «получено до N»

2. Ретрансмиссия

нет подтверждения за таймаут — повторная передача

3. Быстрый повтор

три дублирующихся ACK — повтор без ожидания таймаута

↓ Доп. факт

Алгоритм Нагла и TCP_NODELAY

  • Проблема: приложение пишет мелкими порциями — сеть тонет в крошечных сегментах (40 байт заголовков ради 1 байта данных)
  • Решение Нагла: копить мелкие записи, пока не подтверждены предыдущие данные или не наберётся полный сегмент
  • Плата: дополнительная задержка для интерактивных протоколов — отключается опцией TCP_NODELAY

Завершение соединения

  • Полузакрытие: FIN закрывает одно направление — данные другого направления продолжают доставляться

Данные…дейтаграмма — самостоятельная единица передачи

↓ Доп. факт

Размер пакета: MTU и фрагментация

  • MTU — максимальный размер кадра канального уровня (Ethernet: 1500 байт)
  • сообщение больше MTU — IP разбивает его на фрагменты; сборка выполняется только у получателя
  • повторов на уровне IP нет: потеря одного фрагмента — потеря всего сообщения
  • TCP избегает фрагментации, согласовывая MSS ≈ 1460; в UDP размер контролирует само приложение

Сравнение

TCP или UDP

TCP — с гарантиями

  • соединение устанавливается рукопожатием
  • доставка и порядок гарантируются
  • потери восстанавливаются
  • HTTP, электронная почта, передача файлов, СУБД

UDP — минималистичный

  • соединение отсутствует: передача сразу
  • доставка и порядок не гарантируются
  • минимальные задержки и накладные расходы
  • DNS, DHCP, NTP, потоковое мультимедиа

Выбор — полнота доставки против оперативности.

↓ Доп. факт

QUIC: надёжность поверх UDP

  • транспортный протокол поверх UDP; основа HTTP/3
  • надёжность и упорядоченность — как у TCP, но по отдельным потокам: потеря в одном не блокирует остальные
  • встроенное шифрование TLS 1.3; быстрое восстановление сеанса (0-RTT)
  • смена сети (Wi-Fi → LTE) без разрыва соединения
