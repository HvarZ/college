DNS: разрешение
имён

Что происходит за 20 миллисекунд между Enter и началом загрузки страницы

Введение

Зачем сети «телефонный справочник»

Люди

  • помнят имена: example.com, vk.com
  • имя — бренд: переносится на другой адрес
  • по имени не видно: где сервер, сколько их

Сеть

  • работает с адресами: 93.184.216.34
  • маршрутизация — только по IP
  • адреса меняются: сервер переехал — имя осталось

DNS — распределённая база перевода имён в адреса.

Введение

От одного файла к мировой системе

1970-е — hosts.txt — «справочник интернета»

один файл: имя → адрес; ведёт Стэнфорд, все качают по FTP; машин сотни — и file кончился

1983 — Пол Мокапетрис создаёт DNS в USC

распределённая иерархия, кэширование, делегирование — принципы живы без изменений

1987 — RFC 1034 / 1035 — действующая спецификация

тот же протокол держит современный интернет: миллиарды имён, миллионы запросов в секунду

Наследие hosts.txt живо: файл hosts в ОС проверяется до DNS — вернёмся к нему в конце

Введение

День, когда Facebook исчез

6 часов

4 октября 2021 · facebook.com, whatsapp, instagram

  • Ошибка конфигурации сняла объявления маршрутов Facebook из BGP — сеть «ушла в себя»
  • Их DNS-серверы стали недостижимы → имя facebook.com перестало разрешаться
  • Для мира это выглядело так: «весь Facebook упал» — хотя «упал» только справочник
  • Инженеры ехали в ДЦ: удалённый доступ тоже резолвился через их же DNS…

Нет DNS — «нет интернета», даже если серверы живы.

Как устроено

Анатомия доменного имени

  • Зона — часть дерева, которую ведёт один авторитативный сервер (или их группа)
  • У одного имени — сколько угодно записей: несколько адресов, MX, TXT…

Как устроено

Кто владеет именами

ICANN→ реестры зон (.ru — координационный центр)→ регистраторы→ вы: арендуете домен
  • Домен нельзя купить навсегда — только арендовать на год и продлевать
  • Регистратор назначает NS-серверы: где лежит ваша зона
  • Цены: .ru — от ~200 ₽/год; .com — ~10–15 $/год; «красивые» домены — аукционы
  • Не продлил — через льготный период имя уходит свободным: бесчисленные проекты так теряли свои домены

Правая кнопка мыши по сайту не даст ответа «чей домен» — а WHOIS даст: владелец, регистратор, даты

Механика

Рекурсивный и итеративный запрос

Корень «.»

«не знаю адрес, но знаю, кто ведёт .ru»

TLD .ru

«не знаю адрес, но знаю NS зоны example.ru»

Авторитативный

«знаю всё о зоне: вот A-запись»

клиент→ резолвер: сделай всё за меня→ корень→ .ru→ авторитативный→ ответ в кэш
  • Рекурсивный запрос — клиент→резолвер: «дай готовый ответ»
  • Итеративные — резолвер сам обходит дерево по подсказкам
  • Итог: клиент ждёт одного ответа, всю беготню делает резолвер

↓ Доп. факт

Резолверы: кто делает беготню

Ваш провайдер

выдаётся автоматически с DHCP; видит все ваши запросы

8.8.8.8 · Google

публичный, быстрый; ответы из огромного кэша

1.1.1.1 · Cloudflare

позиционируется как «приватный»: не логирует

  • Смена резолвера — это выбор: скорость / приватность / блокировки
  • Сетевые фильтры и «заблокированные сайты» часто работают именно на уровне резолвера

Механика

Почему DNS ездит по UDP

UDP: один запрос — один ответ

  • без рукопожатия: 1 пакет вместо 3+2
  • запрос кэшируется — большинство ответов мгновенные
  • потерялся — клиент просто спросит снова

TCP: запасной путь

  • ответ не влез в дейтаграмму — флаг truncated
  • резолвер повторяет по TCP: порт 53 тоже
  • передача целых зон между серверами — только TCP

Короткий запрос-ответ без состояния — идеальная работа для UDP.

↓ Доп. факт

Сколько влезает в ответ

  • Изначальный лимит UDP-дейтаграммы DNS — 512 байт: несколько записей + метки
  • EDNS0 (расширение, RFC 6891): договорились о пакетах до 4096 байт — так живут длинные DNSSEC-ответы
  • Больше — флаг truncated и повтор по TCP
  • Поэтому «много A-записей для балансировки» — десяток-другой, не сотни: ответ должен оставаться компактным

Механика

Типы записей

A
имя → IPv4-адрес: example.ru → 93.184.216.34
AAAA
имя → IPv6-адрес («quad-A»)
CNAME
псевдоним: имя → другое имя
MX
почтовый сервер зоны с приоритетом — из темы почты
NS
какой сервер авторитативен для зоны
TXT
произвольный текст: SPF/DKIM, подтверждение владения доменом
SOA
паспорт зоны: серийный номер, таймеры обновления

У одного имени — записи нескольких типов одновременно: A + AAAA + MX + TXT…

↓ Доп. факт

TTL: почему «DNS уже починили, а у вас нет»

  • У каждой записи — TTL (time to live): сколько секунд ответ считать свежим
  • Типовые значения: от 60 с (балансировка) до 86 400 (сутки)
  • Сменили адрес сервера, а TTL был сутки — половина интернета сутки ходит на старый. Поэтому миграции начинают со снижения TTL заранее
  • Кэшируется и отрицательный ответ (NXDOMAIN): «такого имени нет» — тоже на какое-то время

Правило миграций

За двое суток до переезда: TTL → 300; переезд; проверка; TTL обратно

Практика

nslookup: три команды

# обычное разрешение: покажет адрес и резолвер
nslookup example.com

# конкретный тип записи - почтовые серверы домена
nslookup -type=mx gmail.com

# спросить конкретный сервер, а не системный
nslookup example.com 8.8.8.8
  • Работает одинаково в Windows, macOS, Linux — уже было в домашке
  • В ответе всегда два блока: кто отвечал (резолвер) и что ответил

↓ Доп. факт

dig: ответы как они есть

$ dig example.com

;; QUESTION SECTION:      ; что спросили
;example.com.     IN  A
;; ANSWER SECTION:        ; что ответили (с TTL!)
example.com.   86400  IN  A   93.184.216.34
;; флаги: qr aa rd ra      ; aa = авторитативный ответ
;; Query time: 12 msec     ; время запроса

dig показывает TTL прямо в ответе — и кто авторитативен. Инструмент администратора; в Windows — nslookup или WSL

Кэширование

Три уровня кэша

браузер→ операционная система→ резолвер→ авторитативный
  • Браузер: кэширует агрессивно — повторное открытие вкладки не порождает DNS вообще
  • ОС: системный кэш + файл hosts — проверяется до запросов в сеть
  • Резолвер: общий кэш для тысяч пользователей — чаще всего ответ уже готов
сброс в Windows: ipconfig /flushdns Chrome: chrome://net-internals/#dns

Полный проход по дереву — редкость: 90%+ запросов заканчиваются на первых двух уровнях

Глубже

Обратное разрешение: PTR

93.184.216.34→ 34.216.184.93.in-addr.arpa→ PTR-запись→ имя хоста
  • Тот же DNS, только адрес разворачивается и дописывается в специальную зону
  • Зона in-addr.arpa — гигантское дерево на все IPv4-адреса интернета
  • Владелец блока адресов ведёт PTR для своих IP у провайдера

↓ Доп. факт

Кто полагается на PTR

  • Почтовые серверы: «у тебя нет PTR — твои письма в спам»: крупные получатели проверяют соответствие PTR и HELO
  • Логи: читать «пришёл с mail.example.ru» приятнее, чем «с 93.184.x.x»
  • Антиспам и репутация: списки репутаций адресов завязаны на обратные имена

Практика

Поднимаете свой почтовый сервер — сначала PTR у провайдера, потом всё остальное

Глубже

IPv6: вторая адресная книга

A + AAAA у одного имени

имя знает оба адреса: IPv4 93.184.216.34 и IPv6 2606:2800:…

Кого выбрать?

клиент с IPv6 предпочитает AAAA; нет — fallback на A: dual-stack

  • Обратная зона для IPv6 — ip6.arpa: 32 «ниббла» адреса задом наперёд
  • «Сайт недоступен по IPv6, хотя по IPv4 работает» — забытая AAAA-запись: классика инцидентов

Диагностика

Отказ DNS: симптомы

Как выглядит

  • «Не удаётся resolve DNS / найти сервер»
  • мессенджеры работают, сайты — нет
  • по IP (http://93.184.216.34) — открывается!

Проверяем по шагам

  • nslookup example.com — резолвер вообще отвечает?
  • nslookup example.com 8.8.8.8 — другой резолвер поможет?
  • работает с 8.8.8.8 → проблема в резолвере провайдера
  • нет и там → проблема в зоне или сети

«Сайты не открываются» — в половине случаев это DNS, а не «интернет».

Безопасность

Открытый UDP и подмены

  • Ответ по UDP приходит без подтверждения подлинности: кто первый ответил — тот и прав
  • Спуфинг: подложить фальшивый A-запись → пользователь на «vk.com», который совсем не vk.com
  • DNSSEC: каждая зона подписана; записи несут криптографическую подпись, цепочка доверия — от корня
  • Проверяющий резолвер отбивает подделку; пока включён не везде — .ru подписан, .com — частично

Знакомая механика из HTTPS: та же идея цепочки доверия, что у сертификатов

↓ Доп. факт

DoH и DoT: шифрование запросов

  • Классика: резолвер видит все ваши домены, провайдер — тоже; наблюдателю видно, «к чему вы ходите»
  • DoT — DNS поверх TLS: порт 853, отдельный канал
  • DoH — DNS поверх HTTPS: порт 443, неотличим от обычного трафика; браузеры используют по умолчанию
  • Побочный эффект: корпоративные фильтры и «родительский контроль» на уровне DNS перестают работать — источник споров

Глубже

geo-DNS: почему «сайт рядом»

Одно имя — разные ответы

резолвер из Москвы получает адрес сервера в Европе, из Владивостока — в Азии

Кто решает?

авторитативный сервер смотрит на источник запроса (резолвер клиента) и выбирает ближайший ЦОД

  • Так работают CDN (Cloudflare, Akamai, CDNvideo): миллионы имён, ответ подбирается географией
  • Плюс балансировка: у имени десяток адресов, клиент берёт «первый живой»
  • Поэтому «у вас сайт медленный, а у нас быстрый» может быть буквально разными серверами

Практика разработки

DNS в работе разработчика

/etc/hosts

локальная подмена имён до DNS: «считай test.local моим сервером» — отладка без домена

Медленный первый запрос

TTL истёк — резолвер идёт по дереву: десятки мс. Лечится: TTL повыше + тёплый резолвер

Миграции

переезд сервера = смена A-записи: заранее снизить TTL, сменить, проверить с 8.8.8.8, вернуть

Файл hosts: Windows — C:\Windows\System32\drivers\etc\hosts, macOS/Linux — /etc/hosts

↓ Доп. факт

Как домен попадает на серверы

  • Купили домен → у регистратора указали NS-серверы (например, ns1.cloudflare.com)
  • Регистратор прописывает NS-записи в зоне .ru — домен «делегирован»
  • На NS-серверах заводите файл зоны: A, MX, TXT… У Cloudflare это веб-интерфейс
  • Делегирование занимает до 24–72 часов — пока все резолверы увидят новые NS

Частая ошибка

Сменили NS у регистратора, а записи зоны забыли перенести: домен «жив», но отвечает пустотой

Демонстрация

Резолвер в терминале

nslookup example.com          # кто наш резолвер и что ответил
nslookup -type=mx vk.com      # почтовые серверы живого домена
nslookup -type=ns example.com # кто авторитативен за зоной
nslookup example.com 1.1.1.1  # другой резолвер - другой взгляд

Четыре команды — и вся механика урока видна за минуту.

Итог схемы

Один запрос за 60 секунд

Enter→ кэш браузера?→ кэш ОС / hosts?→ резолвер→ корень → TLD → авторитативный→ адрес в кэш→ TCP к серверу

  • И только после DNS начинается то, что мы изучали раньше: TCP-рукопожатие и HTTP
