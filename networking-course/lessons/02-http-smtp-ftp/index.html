HTTP

HTTP: запрос — ответ

TCP-соединение→ запрос→ ответ→ закрыть / переиспользовать
  • Текстовый протокол: сообщения читаются человеком
  • Обмен инициирует только клиент; сервер отвечает
  • Без состояния (stateless): каждый запрос самодостаточен

HTTP

Структура запроса

GET /orders/42 HTTP/1.1          ← строка запроса: метод · путь · версия
Host: api.example.com            ← заголовки: имя-значение
Accept: application/json
User-Agent: curl/8.4.0
                                 ← пустая строка — разделитель
(тело: у GET его нет; у POST — данные)

Первая строка + заголовки + пустая строка + тело — так устроен каждый HTTP-запрос

HTTP

Структура ответа

HTTP/1.1 200 OK                  ← статусная строка: версия · код · фраза
Content-Type: application/json
Content-Length: 27

{"id": 42, "status": "paid"}

↓ Доп. факт

Идемпотентность на практике

  • Сеть сбоит → клиент повторяет запрос. GET и PUT повторять безопасно, POST — нет: двойной POST /orders = два заказа
  • Защита дублей POST: заголовок Idempotency-Key — сервер запоминает ключ операции и не выполняет её дважды
  • Правило: 4xx — исправляй запрос (повтор бессмыслен), 5xx — повторяй позже с задержкой

Ключевые заголовки

Host

какой сайт на сервере с многими сайтами (виртуальный хостинг)

Content-Type

формат тела: application/json, text/html

размер тела в байтах — граница сообщения

Заголовки — метаданные обмена: их десятки стандартных и сколько угодно своих (X-…)

HTTP

Cookie: состояние поверх stateless

первый запрос→ Set-Cookie: session=abc123→ клиент хранит cookie→ Cookie: session=abc123→ сервер узнаёт клиента
  • Протокол без состояния — сервер не помнит клиентов между запросами
  • Cookie — метка клиента: сервер выдаёт, браузер возвращает в каждом запросе
  • Сессия: запись о пользователе на сервере + её идентификатор в cookie

HTTP

HTTPS: HTTP + TLS

Шифрование

посредник видит бессмыслицу, а не пароли и карты

Целостность

подмена данных в пути обнаруживается

Подлинность

сертификат — паспорт сервера, выданный центром доверия

Порт 443; внутри — обычный HTTP, но в зашифрованном виде

↓ Доп. факт

Как TLS строит канал

  • Рукопожатие: ClientHello / ServerHello → сервер предъявляет сертификат → браузер проверяет цепочку доверия до корневого центра
  • Стороны согласуют сеансовый ключ (ECDHE): асимметричная криптография — только для обмена ключом
  • Дальше весь трафик шифруется симметрично — быстро
  • Асимметрия медленная: она защищает только «передачу ключа», симметрия — сами данные

↓ Доп. факт

WebSocket: когда HTTP мало

  • HTTP: говорит всегда клиент — сервер не может «толкнуть» данные сам
  • WebSocket: HTTP-запрос с заголовком Upgrade: websocket → соединение остаётся и становится двусторонним
  • Обе стороны шлют кадры независимо; накладные расходы — единицы байт
  • Где: чаты, уведомления, котировки — всё «в реальном времени»

Электронная почта

Отправка ≠ получение

SMTP

отправка и передача между серверами
порты 25, 587

POP3

скачивание писем на устройство
порты 110, 995

IMAP

синхронизация с папками на сервере
порты 143, 993

Письмо идёт: клиент → SMTP → сервер отправителя → SMTP → сервер получателя → POP3/IMAP → клиент

SMTP

Сессия SMTP

S: 220 mail.example.com ESMTP ready       ← сервер представился
C: EHLO client.net                        ← клиент — в ответ
S: 250 OK
C: MAIL FROM:<alice@client.net>           ← конверт: отправитель
S: 250 OK
C: RCPT TO:<bob@example.com>              ← конверт: получатель
S: 250 OK
C: DATA                                   ← перехожу к тексту письма
S: 354 Start mail input
C: From: Alice … Subject: Отчёт …         ← заголовки и тело письма
C: Текст письма.
C: .                                      ← точка в пустой строке = конец
S: 250 OK: queued
C: QUIT

Диалог команд и кодов — как у HTTP, но инициирует отправитель

↓ Доп. факт

MIME и судьба письма

  • MIME: заголовки Content-Type и multipart позволяют вкладения и не-ASCII тексты (кириллицу) — изначально SMTP был только 7-битным ASCII
  • Релеи: письмо проходит несколько SMTP-серверов; каждый добавляет строку Received: — маршрут письма видно в заголовках
  • SPF / DKIM / DMARC: проверки «действительно ли отправитель тот, за кого себя выдаёт» — без них письмо улетает в спам

Почта

POP3 и IMAP

POP3 — забрать

  • скачивает письма на устройство, удаляет с сервера
  • одно устройство, работа офлайн
  • папки — только локально

IMAP — синхронизировать

  • письма и папки живут на сервере
  • много устройств согласованы
  • состояние прочитано/непрочитано — общее

Сегодня пользователь чаще видит не POP3/IMAP напрямую, а веб-интерфейс — но это HTTP-надстройка над той же почтовой системой

FTP

FTP: два канала

2

канала у одной сессии

  • Канал управления (порт 21): команды — USER, PASS, LIST, GET, PUT — и коды ответов
  • Канал данных: отдельное соединение — само содержимое файла или листинг каталога
  • Управление не блокируется перекачкой: можно послать ABOR — прервать передачу

↓ Доп. факт

Активный и пассивный режим

  • Активный: сервер сам подключается к клиенту для канала данных — у клиента должен быть видимый адрес
  • За NAT и файрволом активный режим ломается: NAT прячет адреса клиентов
  • Пассивный: клиент сам открывает второе соединение к серверу — проходит через NAT, поэтому стал стандартом

FTP

Наследники FTP

FTPS

FTP + TLS: тот же протокол, шифрованный (порт 990)

SFTP

передача файлов поверх SSH (порт 22) — другой протокол при схожем имени

  • Чистый FTP передаёт пароли и данные открытым текстом
  • Два канала + проблемы с NAT — архитектурное наследие 1971 года (RFC 114 → 959)
