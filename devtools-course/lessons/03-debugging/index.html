Введение

Тестирование и отладка

Тестирование

  • находит симптом: отказ, неверный результат
  • отвечает на вопрос «что не работает?»
  • инструменты: тест-кейсы, JUnit, чек-листы

Отладка

  • ищет причину: дефект в коде или данных
  • отвечает на вопрос «почему не работает?»
  • инструменты: дебаггер, логи, профилировщик

Тестирование нашло отказ — отладка ведёт от отказа к строке, которая его вызывает

Введение

Отладка — это научный метод

гипотеза→ эксперимент→ вывод↺
  • Гипотеза: «подозреваю, что массив пуст, когда приходит пустая строка»
  • Эксперимент: остановить программу и посмотреть — проверка, а не гадание
  • Гипотеза подтвердилась — локализовали; нет — новая гипотеза

Меняй одну вещь за раз — иначе не узнаешь, что подействовало.

Дебаггер · IDEA

Точка остановки: заморозка времени

Run

программа выполняется от начала до конца; наблюдаем только результат

Debug

на breakpoint поток замирает — состояние можно рассмотреть

  • Breakpoint — метка на строке: «остановись здесь» (клик по полю слева)
  • В остановке видны: значения переменных, место выполнения, стек вызовов
  • Дебаггер не меняет код: он делает состояние программы наблюдаемым

Дебаггер · IDEA

Три шага выполнения

Step Over
выполнить строку целиком и перейти к следующей — не входя в вызываемые методы
Step Into
шагнуть внутрь вызова — вглубь по стеку
Step Out
выполнить текущий метод до конца и вернуться к вызывающему

Тактика: Over по своему коду; Into — только когда подозреваемый именно этот вызов

↓ Доп. факт

Условные точки остановки

  • Breakpoint в цикле на десять тысяч итераций? Условие: останавливаться только при i == 9999 или name.equals("Иванов")
  • Evaluate Expression: в остановке посчитать любое выражение в текущем контексте — items.size(), total * 0.9 — без изменения кода
  • Также полезны: log breakpoint — не останавливать, а печатать значение; hit count — стоп на N-м срабатывании

Смысл

Дебаггер настраивается под задачу — большинство «неудобных» остановок решаются условием

Дебаггер · IDEA

Наблюдение и правка на лету

Watches

закрепить выражения за экраном: items.size(), total > limit — меняются с каждым шагом

Set Value

изменить переменную прямо в остановке и продолжить выполнение — «что если discount = 0.9?» без перезапуска

Эксперименты «что если» без правки кода и пересборки — в этом сила дебаггера

Дебаггер · IDEA

Стек вызовов: как я сюда попал

process():  EchoService.java:14     ← сейчас здесь
handle():   ClientHandler.java:31
run():      ClientHandler.java:22     ← каждый кадр — контекст вызова
...
  • Frames — путь вызовов сверху вниз: от текущей строки до main
  • Клик по кадру — переключение в тот вызов: видны его переменные
  • Стек отвечает на половину вопросов отладки: кто вызвал и с чем

↓ Доп. факт

Drop Frame и Attach to Process

  • Drop Frame: отмотать верхний вызов — вернуться в точку перед ним и пройти заново, с уже известными данными. «Переиграть» ошибочный шаг
  • Attach to Process: подключить дебаггер к уже работающему приложению — без перезапуска. Работает и для удалённого сервера (по порту агента)
  • Attach — стандарт для отладки долгоживущих процессов, которые нельзя останавливать

Почему System.out — плохо

Не выключить

печать остаётся в проде — навсегда

Нет уровней

трассировка и авария — одним цветом

Тормозит

вывод в консоль — медленный I/O, в цикле — катастрофа

Нет контекста

ни времени, ни потока, ни источника — голая строка

println — для первого взгляда; логгер — для системы.

Логирование · Java

Логгер: уровни и формат

private static final Logger log =
        LoggerFactory.getLogger(EchoService.class);

log.trace("вошли в process()");
log.debug("line = {}", line);            // подстановка, не конкатенация
log.info("клиент подключился: {}", addr);
log.warn("пустая строка - пропускаю");
log.error("обработка упала", exception); // + stack trace
TRACE→DEBUG→INFO→WARN→ERROR: порог настраивается SLF4J — фасад, Logback — реализация

↓ Доп. факт

Корреляция записей: MDC и requestId

  • Проблема: запросы от разных клиентов перемешиваются в общем логе
  • MDC (Mapped Diagnostic Context): карта «метка → значение», живёт в потоке; в начале запроса кладём requestId — и каждая запись лога его содержит
  • Итог: grep requestId вытянет всю историю одного запроса сквозь все классы

Логирование

Что и сколько логировать

Стоит

  • входы и выходы ключевых операций
  • решения: «лимит превышен — отказ»
  • ошибки с контекстом и stack trace
  • медленные места: «обработка заняла N мс»

Не стоит

  • пароли, токены, персональные данные
  • каждую итерацию цикла
  • одно и то же на каждом уровне стека

Отладочные классы

Диагностика в собственном коде

public final class Debug {                      // утилита отладки
    public static void timed(String what, Runnable code) {
        long t0 = System.nanoTime();
        code.run();
        long ms = (System.nanoTime() - t0) / 1_000_000;
        log.debug("{} заняло {} мс", what, ms);
    }
}

Debug.timed("обработка запроса", () -> service.process(line));
  • Отладочный класс — вспомогательный код диагностики: замеры времени, счётчики вызовов, трассировка входа-выхода
  • Живёт в проекте постоянно; java.util.logging — системный вариант из JDK

↓ Доп. факт

assert в Java

int total = calcTotal(items);
assert total >= 0 : "total отрицателен: " + total;
  • assert условие : сообщение — проверка «внутренней уверенности»
  • Выключены по умолчанию: включаются флагом -ea (enable assertions)
  • Не для валидации пользовательских данных: в проде проверка может быть просто выключена — assert — инструмент разработчика, а не защиты

Диагностика

Stack trace: читаем правильно

java.lang.StringIndexOutOfBoundsException:
  begin 0, end -1, length 0          ← что случилось
  at java.lang.String.substring(String.java:...)
  at EchoService.process(EchoService.java:14)   ← ПЕРВАЯ «СВОЯ» строка
  at ClientHandler.handle(ClientHandler.java:31)
  ...
  • Первая строка — исключение и сообщение; дальше — путь от места броска вверх
  • Идти к первой строке своего кода — библиотечные кадры редко виноваты
  • Строка вида Caused by: внизу — первопричина, читать её

↓ Доп. факт

Цепочки исключений

try {
    order.process(items);
} catch (IOException e) {
    throw new ServiceException("обработка заказа упала", e); // ← причина внутрь
}

Оборачивая исключение, всегда передавайте исходное — тогда в логе появится Caused by с настоящей причиной. Потерянная причина — потерянные часы отладки

Диагностика

Измерять, а не угадывать

Профилировщик

в IDEA встроен: Run with Profiler; показывает, где программа проводит время

Hotspot

метод-«пожиратель»: единицы методов съедают основное время

Правило

оптимизировать только измеренное, а не «кажется, тут медленно»

«Мне кажется, тормозит здесь» — не аргумент. Аргумент — профиль.

Демонстрация

Чиним echo под дебаггером

String process(String line) {
    return line.substring(0, line.length() - 1);   // «убираем \n»
}
  • Симптом: на "" — StringIndexOutOfBounds; на строках — пропадает последняя буква
  • Breakpoint на строке → смотрим line: пустая строка даёт конец -1
  • Причина найдена; фикс → тест на оба случая — регрессия закрыта
