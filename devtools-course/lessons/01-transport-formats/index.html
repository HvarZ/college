↓ Доп. факт

Идемпотентность и коды ответов

  • Идемпотентность: повтор запроса не меняет результат. GET, PUT, DELETE — идемпотентны; POST — нет (двойной POST = два заказа)
  • Поэтому повторные попытки безопасны только для идемпотентных методов
  • 4xx — ошибка на стороне клиента: повтор без изменения запроса бессмыслен (400, 401, 403, 404)
  • 5xx — ошибка на сервере: повтор позже оправдан (500, 503)

Правило интеграции

Получил 5xx — повтори с задержкой; получил 4xx — исправляй запрос, а не жди чуда

Транспорт

WebSocket: двусторонний канал

HTTP: полудуплекс

  • обмен инициирует только клиент
  • сервер не может «толкнуть» данные сам
  • выход: опрос (polling) — расточительно

WebSocket: полный дуплекс

  • одно соединение TCP — обе стороны шлют кадры
  • устанавливается через HTTP-рукопожатие
  • минимальные накладные расходы

Применение: чаты и уведомления, котировки биржи, состояние в реальном времени

Транспорт · Очереди

Очереди сообщений

производитель→ брокер: очередь→ потребитель
  • Развязка: модули не обращаются друг к другу напрямую — только к брокеру
  • Асинхронность: потребитель обрабатывает, когда готов; пик сглаживается очередью
  • Гарантии: сообщение сохранится, даже если получатель временно недоступен

Брокеры: RabbitMQ, Apache Kafka, ActiveMQ

↓ Доп. факт

RabbitMQ и Kafka: две философии

RabbitMQ

маршрутизация задач: сообщение уходит одному потребителю и удаляется после подтверждения

Kafka

распределённый журнал: сообщения хранятся; потребители читают поток и могут перечитать

  • Гарантии доставки: at-most-once (можно потерять), at-least-once (могут быть дубли), exactly-once (дорого)
  • At-least-once + идемпотентный потребитель — практический стандарт

Транспорт

Синхронно или асинхронно

Синхронно · HTTP

  • ответ — немедленно
  • обе стороны должны быть доступны одновременно
  • просто отлаживать: запрос и ответ рядом

Асинхронно · очередь

  • результат — позже, через другое сообщение
  • устойчивость к недоступности и пикам
  • сложнее трассировать цепочку

Нужен ответ — или уведомление о событии?

↓ Доп. факт

Надёжность асинхронного обмена

  • Таймауты: ожидание ответа не бесконечно — иначе модуль «зависает» целиком
  • Повторные попытки: экспоненциальная задержка (1 c → 2 c → 4 c), лимит попыток
  • Идемпотентный потребитель: повторная доставка не ломает результат (проверка «уже обработано?»)
  • Dead-letter очередь: куда попадают сообщения, которые не удалось обработать после всех попыток

Принцип

Отказ — не исключение, а плановый случай: обмен обязан переживать недоступность

Форматы

Сериализация: объект ↔ сообщение

объект Java→ сериализация→ байты: JSON / XML / …→ сеть→ десериализация→ объект Java
  • Формат — договор о том, как объект превращается в байты и обратно
  • стороны могут быть написаны на разных языках — формат это neutral ground

Форматы · JSON

JSON: текстовый формат по умолчанию

{
  "id": 42,
  "customer": "Иванов И. И.",
  "items": [
    { "sku": "A-100", "qty": 2, "price": 9.99 }
  ],
  "paid": false
}
типы: объект · массив · строка · число · bool · null Java: Jackson / Gson Content-Type: application/json

↓ Доп. факт

JSON Schema: контракт полей

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "properties": {
    "id":    { "type": "integer" },
    "customer": { "type": "string", "minLength": 1 }
  },
  "required": ["id", "customer"]
}
  • схема описывает поля, типы и обязательность — договор, проверяемый автоматически
  • валидация на входе: сообщение без обязательного поля отклоняется до обработки

Форматы · XML

XML: размеченные документы

<order id="42">
  <customer>Иванов И. И.</customer>
  <items>
    <item sku="A-100" qty="2" price="9.99"/>
  </items>
  <paid>false</paid>
</order>
  • Элементы — содержимое данных; атрибуты — метаданные (id, sku)
  • строгая вложенность, пространства имён для смешивания словарей
  • Java: JAXB; живёт в конфигурациях (pom.xml), SOAP, документообороте

↓ Доп. факт

XSD и SOAP

  • XSD — схема XML: допустимые элементы, типы, порядок, кратность. Валидация документа — до обработки
  • SOAP — протокол поверх XML: жёсткий конверт (Envelope → Header → Body), встроенные ошибки (Fault), WSDL-контракт
  • Стандарт корпоративного мира: банки, госструктуры, платёжные шлюзы

Итог

XML тяжелей JSON, но строже: схема и конверт принудительны

Форматы · Бинарные

Protobuf: схема и компактность

message Order {
  int64  id       = 1;
  string customer = 2;
  repeated Item items = 3;
}

message Item {
  string sku   = 1;
  int32  qty   = 2;
  double price = 3;
}
  • Схема первична: код и контракт генерируются из .proto
  • каждое поле имеет номер — бинарная запись компактна и устойчива к изменениям схемы

↓ Доп. факт

Размер и совместимость версий

  • Одно и то же сообщение (заказ из примера):
    JSON ≈ 120 байт · XML ≈ 180 байт · Protobuf ≈ 45 байт
  • Номера полей — это контракт: добавлять новые поля можно, менять и удалять номера нельзя
  • Старый код просто игнорирует неизвестные поля — обратная совместимость «из коробки»

gRPC

Протокол вызова удалённых процедур: Protobuf + HTTP/2. Стандарт внутренней связи микросервисов

Java

HTTP-клиент и JSON в Java

HttpClient client = HttpClient.newHttpClient();          // Java 11+

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/orders/42"))
        .header("Accept", "application/json")
        .build();

HttpResponse<String> response =
        client.send(request, HttpResponse.BodyHandlers.ofString());

Order order = new ObjectMapper()                       // Jackson
        .readValue(response.body(), Order.class);
HttpClient — запрос-ответ ObjectMapper — JSON ↔ объект serialization в одну строку: writeValueAsString(order)

Семантика

Контракт и версионирование API

  • API-first: сначала договор (схема), потом реализация — схема документирует и проверяет
  • Версии в пути: /v1/orders → /v2/orders; новая версия не ломает старых клиентов
  • Обратная совместимость: добавлять поля — можно; удалять и переименовывать — нельзя

Контракт труднее изменить, чем код, — его читают чужие программы.
