Введение

Верификация и валидация

Верификация

  • «Делаем ли продукт правильно?»
  • соответствие спецификации, требованиям
  • инструменты: ревью, тесты, статический анализ

Валидация

  • «Делаем ли правильный продукт?»
  • соответствие потребностям пользователя
  • инструменты: приёмка, сценарии использования

Уровни

Пирамида тестов

System · UI

весь продукт целиком — мало, медленно, дорого

Integration

модули вместе — стыки и договорённости

Unit

отдельные методы и классы — много, быстро, дёшево

Основание широкое: быстрые unit-тесты гоняются при каждой сборке, верх — редко

↓ Доп. факт

Критика пирамиды: «трофей»

  • Пирамида — ориентир 2000-х, родом из мира толстой бизнес-логики
  • В приложениях, где ценность — в интеграциях (API, веб), логика тонка: большинство дефектов — на стыках
  • «Тестовый трофей»: больше интеграционных тестов, unit — там, где есть что изолировать

Вывод

Форма набора тестов следует за архитектурой приложения, а не за модой

Виды

Функциональное и нефункциональное

Функциональное

что продукт делает: функции, сценарии, правила

Нефункциональное

как он это делает: производительность, безопасность, удобство, совместимость

нагрузочное — сколько выдержит безопасности — что сломает злоумышленник юзабилити — удобно ли человеку

Методы

Статическое и динамическое

Статическое — без запуска

  • инспекции и ревью кода
  • компилятор: типы, синтаксис
  • анализаторы: линтеры, поиск утечек

Динамическое — запуск

  • ручные проверки по чек-листам
  • автоматические прогоны тестов
  • замеры поведения под нагрузкой

↓ Доп. факт

Статический анализ в IDE

  • Инспекции IDEA: сотни правил — вероятные null-разыменования, незакрытые ресурсы, избыточный код — прямо при наборе
  • SonarLint: тот же класс находок + «code smells» и уязвимости, синхронизация с сервером SonarQube
  • Сильная сторона: находки до первого запуска; слабая — много ложных срабатываний, нужна настройка

Ручное

Где незаменимы руки

Исследовательское

тестировщик учится продукту и проверяет гипотезы одновременно

Первая проверка фичи

свежий взгляд до написания тестов

Удобство и эстетика

«неудобно» — не формализуется в assert

Инструменты ручного тестировщика: чек-листы, тест-кейсы, баг-трекер

Ручное

Тест-кейс и дефект-репорт

Тест-кейс

  • цель: что проверяем
  • предусловия: состояние системы
  • шаги → ожидаемый результат

Дефект-репорт

  • шаги воспроизведения + факт против ожидания
  • severity — влияние на продукт
  • priority — срочность исправления

Severity и priority независимы: опечатка на главной — низкая серьёзность, высокая срочность

Автоматизация

Зачем и почему не всё

Автоматизируем

  • регрессию: проверять старое при каждом изменении
  • повторяемые прогоны: сборка, окружение
  • проверки с данными: сотни входов

Оставляем людям

  • разовые проверки
  • исследовательские сессии
  • оценку удобства и внешнего вида

Тест — это код: ему нужна поддержка, как продукту.

Автоматизация

Unit-тест: изоляция и FIRST

  • Unit-тест проверяет одну единицу (метод, класс) в изоляции от остальной системы

F · Fast

сотни тестов — секунды

I · Independent

порядок и соседние тесты не влияют

R · Repeatable

результат одинаков везде и всегда

S · Self-validating

вердикт зелёный/красный без человека

Автоматизация · Java

JUnit 5: структура теста

class CalculatorTest {

    @Test
    void twoPlusTwoIsFour() {
        // arrange — подготовка
        Calculator calc = new Calculator();

        // act — действие
        int result = calc.add(2, 2);

        // assert — проверка
        assertEquals(4, result);
    }
}
@Test — метод-тест паттерн arrange — act — assert запуск: mvn test

↓ Доп. факт

Параметризованные тесты

@ParameterizedTest
@CsvSource({
    "  1,  1,  2",
    "  2,  3,  5",
    " -1,  1,  0",
    "100,  0, 100"
})
void sumsCorrectly(int a, int b, int expected) {
    assertEquals(expected, new Calculator().add(a, b));
}

Один метод — много наборов данных; упавший набор виден в отчёте отдельно

Автоматизация · Java

Утверждения

assertEquals(4, x)
x равен 4 — иначе тест красный с разницей значений
assertTrue(cond)
условие истинно (и assertFalse наоборот)
assertNull(v) / assertNotNull(v)
значение null / не null
assertThrows(E.class, () -> …)
блок кода бросит ожидаемое исключение
assertAll(…)
группа проверок: собрать ВСЕ результаты, а не падать на первой

Зелёный тест молчит; красный — сообщает, что именно не сошлось

Автоматизация · Java

Заглушки: test double

Dummy

просто заполнить параметр, не используется

Fake

рабочая упрощённая реализация: список вместо БД

Stub

возвращает подставные ответы на вызовы

Mock

проверяет взаимодействия: был ли вызов, с какими аргументами

Библиотека Mockito: @Mock, when(…).thenReturn(…), verify(…)

↓ Доп. факт

TDD: тест раньше кода

RED: тест падает→ GREEN: минимум кода→ REFACTOR: чистим↺
  • Сначала тест, описывающий ожидаемое поведение — потом реализация
  • Эффект: интерфейсы проектируются от использования, тесты покрывают по построению
  • Дисциплина цикла важнее догмы: смысл — уверенность на каждом шаге

Уровни

Интеграционные тесты

  • Проверяют взаимодействие модулей: модуль + модуль, модуль + БД, модуль + файловая система
  • Изоляция уже не полная: вместо настоящей СУБД — in-memory база (H2), вместо сети — тестовый контейнер
  • Ловят то, чего не видят unit-тесты: несовпадение договорённостей на стыках
  • Медленнее и капризнее unit — их в наборе меньше

Организация

Покрытие и CI

JaCoCo: покрытие

доля строк и веток, исполненных под тестами. 100% не цель; падение покрытия — сигнал

CI: прогон на каждый push

сборка → тесты → отчёт. Красная сборка не попадает в общую ветку

Jenkins, GitHub Actions, GitLab CI — инструменты непрерывной интеграции

↓ Доп. факт

Flaky-тесты

  • Flaky — тест, который «иногда падает»: без изменений кода
  • Причины: зависимость от времени, порядка тестов, сети, общей мутабельной среды
  • Опаснее падения: приучает команду к мысли «красный — это нормально», и настоящий дефект проскочит
  • Лечение: детерминизм, изоляция состояния, фиксированные часы и данные
